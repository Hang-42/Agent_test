# 状态监听与交互 Agent 草案

状态：讨论稿，基于用户提出的两 Agent 架构；Agent 是职责划分，不要求每个模块都调用大模型。

## 职责

- 状态监听 Agent：接收成员交互状态、用户请求、设备及执行事件；检查新鲜度、置信度、上下文和照护者设置，识别适当的触发事件并交给交互 Agent。持续感知不等于持续发起交互；需支持等待、静默、取消、冷却和重复事件过滤。
- 交互 Agent：结合事件、当前活动、允许使用的相关本地记忆及场景策略，决定等待、询问、互动、暂停或结束；生成适当内容，通过受约束的接口请求控制层显示、播放或执行技能，并根据用户回应和执行结果调整。
- 本地记忆模块：独立管理读取和写入权限、来源、保存期限、查看与删除。交互 Agent 生成记录候选，不绕过规则直接写入长期记忆；观察、用户陈述与模型推断分开。
- 控制层：校验并执行动作，反馈成功、失败、取消等状态；独立安全机制优先，可拒绝或停止动作。

## 流程

感知状态或用户事件 → 状态监听 Agent 判断是否触发 → 交互 Agent 读取必要上下文及获准的记忆 → 请求控制层执行 → 获取执行反馈和用户新回应 → 继续、等待、暂停或结束 → 记忆模块按规则处理记录候选。用户停止、照护者干预和安全事件可打断流程；安全停止不依赖 Agent。

## 设计约束

情绪输出为不确定估计，允许未知，不能单凭该标签推定儿童需要干预；不因没有回应就自动启动活动。应定义优先级、重复触发过滤、交互频率和冲突处理。LLM 为可选组件，外部 API 会传输请求内容，须遵守项目隐私边界。语义地图、任务状态和设备反馈均可在需要时供交互 Agent 使用。
